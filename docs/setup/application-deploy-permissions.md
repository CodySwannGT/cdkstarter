# Application deployment permissions

The GitHub OIDC role is an application deployer. Infrastructure administrators own bootstrap, account-wide IAM, networks, execution roles and the protected permission ceiling. Application credentials cannot assume CDK bootstrap roles or arbitrary roles, replace/remove boundaries, update role trust, or modify protected policies. The human-held observer request #23 is unchanged.

Configure `github.applicationDeploy` with exact `stackPrefix`, `resourcePrefix` and `applicationRoleNames`. Prefixes end in `-` and exclude wildcards. Every allowed application role name starts with the resource prefix. If omitted, the default namespace is `infrastructureRepo-stageName-` with one `runtime` role. Only the configured application resource namespace is deployable. Supported grants cover Lambda, DynamoDB, S3, logs, EventBridge and SSM resources in that namespace plus necessary network discovery. Additional services require a reviewed scoped policy change.

Synthesis creates `${resourcePrefix}ApplicationBoundary` and `${resourcePrefix}CloudFormationExecution`. The boundary is attached to both the caller and the CloudFormation executor. The caller passes only that executor to CloudFormation. Created application roles must include this same boundary; specify `permissionsBoundary: iam.ManagedPolicy.fromManagedPolicyArn(...)` on each role in application CDK code. The output `ApplicationBoundaryArn` identifies the ceiling. Approved application roles can be passed only to Lambda, ECS tasks or EventBridge. Role and policy writes outside the allowlist are denied.

Deploy application stacks with CloudFormation CreateStack/UpdateStack/DeleteStack and the explicit `ApplicationExecutionRoleArn` output as `RoleARN`. Use the AWS CloudFormation SDK or explicit `aws cloudformation create-stack`, `update-stack` and `delete-stack` commands with `--role-arn` and an application asset bucket under the configured prefix. An existing CDK or framework workflow must adapt its synthesizer and deployment method to this contract rather than assume the general bootstrap deployment path. The starter does not grant bootstrap-role assumption. Change-set creation/execution is denied because executing an existing change set cannot require an explicit executor in that request and could reuse a privileged stack service role. This is an intentional restriction of the former general account administrator policy.

Administrators must reserve a fresh application role namespace, or attach the ceiling to every existing allowlisted application role before enabling these credentials. No imported role is silently declared bounded. Existing application stacks must migrate to the protected executor. Existing general deployment workflows need this configuration and asset/synthesizer migration, rather than reuse of an administrator CloudFormation executor. Infrastructure bootstrap retains its separate administrator-controlled path. This implementation performs no AWS deployment or existing consumer update.

The offline tests evaluate actual inline grants intersected with the attached managed boundary, including explicit denies, missing condition keys and representative positive/negative ARNs. They prove this policy contract rather than live AWS behavior. Administrators must also control resource policies and external credentials; existing external grants are not discovered by offline synthesis.

Sources: [IAM boundary evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html), [CloudFormation service roles](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-iam-servicerole.html), [IAM boundary and PassRole condition keys](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_iam-condition-keys.html).
